## What holds up (verified, not re-litigated)
- **PRD traceability:** all 114 ACs and 12 NFRs map to a design ref and tests; spec.md ↔ spec.json agree on endpoints, contracts, NFR targets and AC→test mapping (only nit: FT-14 is not named in JSON, see A-10).
- **Config → `preview-on-pr` chaining (DD-2 / V-1):** claim is consistent with flux-config source. `generate-webapp-config` opens the PR with `secrets.SVC_GITHUB_TOKEN` via `peter-evans/create-pull-request@v7` on `auto/gen-<env>-<app>`; `preview-on-pr` triggers on `pull_request` to `main` with a `clusters/{sand,devsand}/**/apps/**` path filter, which the generated PR satisfies; `workflow_dispatch` via `GITHUB_TOKEN` is exempt from the no-recursion rule; `delete-branch: true` + fixed branch gives same-PR re-ship. Residual risks are in A-3 and A-10, not in the claim.
- **Pattern compliance:** no datastore (GitHub + ACR only); dual-App split is explicit per operation (§4.3) and the Code App is never used for flux-config reads; express-validator on every field; ship-id vs request-id separation has precedent (legacy `aks-status-by-correlation` already logs `request_correlation_id`); Vue work lives in `srcV2` with its own `'ship'` `PageId`; `AKSDeployPage.vue`/`AKSInstalledAppsPage.vue` untouched; server-minted `correlation_id` is an improvement over `POST /api/aks-deploy`, which accepts a client-supplied one.
- **Open human decisions H-1…H-8:** handled as explicit, scoped blockers/assumptions with fail-closed defaults (H-1 → `preview.state='not_configured'`, H-2 → provider `none`, H-3 → `SHIP_ACR_READ_ENABLED=false`, H-4 → empty = nobody). Judgement: acceptable, subject to the consistency fixes in A-1, A-4, A-5.

## Blocking Findings
- [ ] **B-1 — No architecture deep-dive or ADR although the Architect's own escalation triggers fire** — spec.md §2.1 last line ("No separate architecture deep-dive doc or ADR is produced"); `architect.agent.md` "Escalation Triggers" — Round-1 dimension 9. The spec introduces (a) a new architectural pattern (five trust zones Z0–Z4 with untrusted-code execution on GitHub-hosted runners, job-output-only trust rules), (b) a new status data plane (check-run annotations as the stateless status channel, DD-3), (c) a cross-repo workflow-as-backend (flux-config owns the pipeline), (d) a pluggable identity seam (DD-4), and (e) a **violated existing pattern**: `CLAUDE.md` mandates "long-running operations always go through the status-modal + polling pattern"/`useWorkflowPolling`; DD-6 replaces it (also contradicts AC-013-2 wording, H-8). Each is a listed trigger ("new architectural pattern", "existing pattern violated with rationale"). The spec offers to "promote DD-2/DD-4/DD-11 to ADRs if the Challenger asks" — this is that ask. **Fix:** author `docs/architecture/ship-from-repo-architecture.md` (trust zones, data-flow rules, status channel, identity seam, cross-repo ownership) and ADRs `docs/adr/20261022-ship-config-handoff-dispatch-and-wait.md` (DD-2), `…-ship-status-via-annotations.md` (DD-3), `…-ship-identity-provider-seam.md` (DD-4), `…-ship-own-polling-composable.md` (DD-6, records the pattern deviation and what would change if PM rejects H-8), `…-ship-workflow-ref-and-environments.md` (DD-11); link them from spec.md §2.1 and spec.json `dependencies`/`technical.decisions`.

- [ ] **B-2 — Security-gate and status-channel integrity: attacker-controlled text can forge "Scan results: PASSED" and trusted `ship.result` annotations** — §3.4 `scan` ("Pass only if output contains `Scan results: PASSED`"), §3.2 rule 2, §3.5 "Trusted results", T9, BT-11, WT-08/WT-11 (AC-006-1, AC-006-4, NFR-005, AC-004-8). Wiz output for an image contains attacker-controlled strings (package names, file paths, labels, layer commands). (1) A substring/“contains” match on free-form output lets a hostile image embed `Scan results: PASSED` in a package name and pass a findings-laden scan. (2) Trusted jobs (`prepare` echoing git/clone errors and repo-derived text; `scan` echoing findings) write to a log that the runner parses for workflow commands, so a line beginning `::notice title=ship.result::{…}` in that text is a **forged annotation on a trusted job** — the design's rule "decisions come from trusted-job annotations only" is then defeated, and `settings`/`skipConfig`/`code` can be spoofed. The spec only models forged annotations from the *build* job (BT-11, §7.4 case 8), and says nothing about escaping the payload (`%`, CR, LF must be percent-encoded in a workflow-command message), which also matters because findings text goes into the ≤4 KB JSON. **Fix:** (a) gate on `wizcli` exit status **and** structured output (`--format json`/`-o` parsed with `jq`; policy verdict field), never a substring of human output; if only text is available, require an anchored whole-line match on the final line *and* exit 0; (b) wrap every step that echoes untrusted text in `::stop-commands::<random>` … `::<random>::` (or redirect it to a file that is only displayed after sanitising `::`), and emit `ship.result` only from a dedicated `emit-result.sh` step using `jq -c` plus `%`/`\r`/`\n` encoding; (c) add tests: WT-08b (image whose package name/label contains `Scan results: PASSED` + a high finding ⇒ `SECURITY_GATE_FAILED`), WT-11b (repo/Wiz text containing `::notice title=ship.result::` ⇒ ignored/escaped), BT-11 case "forged annotation from a trusted job log line"; document in §3.2 that trusted-job logs are also untrusted *text*.

- [ ] **B-3 — Credential exposure on `ubuntu-latest` is not controlled for the steps that touch attacker-controlled bytes** — §3.2 Z2 row, §3.4 `prepare` steps 3/6/7 and `publish` steps 1/2/4, T5, T15 (NFR-003, NFR-005, AC-004-6). PRD §4 states every `ubuntu-latest` pod is injected with `ARM_CLIENT_SECRET`, `GH_APP_PRIVATE_KEY`, an SSH key and a pre-existing `az` login. The spec neutralises only the `az` login (`AZURE_CONFIG_DIR`). It does not address: the other injected secrets being present in the environment of `git clone` of a hostile repo and of `tar` over the hostile tree (T15 hardens git config but not the process environment, global/system git config, `GIT_SSH_COMMAND`/SSH key, or `HOME`); and `publish` parsing the **attacker-controlled image tar** with `crane` (push/mutate/layer-digest assertion) under the AcrPush identity on that same runner — T5 reasons about a parser bug in `scan` (low privilege) but the same bytes are parsed again in the highest-privilege zone. Also, the Code App private key is copied into the `ship-prepare` environment; per CLAUDE.md that app is the code-deployment app (used by `/api/add-code-repo`), so its key is not read-only even though the minted token is down-scoped. **Fix:** add a "Z2 hygiene" subsection and make it testable: step-level (not job-level) secret env; run clone/tar/crane under `env -i PATH=… HOME=$RUNNER_TEMP/h` with `GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_SYSTEM=/dev/null GIT_CONFIG_NOSYSTEM=1 GIT_TERMINAL_PROMPT=0`, https-only (`protocol.allow=never` except https), no SSH agent/key; token passed via `GIT_ASKPASS` file, never in a URL; `unset ARM_* GH_APP_PRIVATE_KEY` for non-minting steps; structural pre-validation of the tar (manifest-only, layer count/size caps, no unexpected members) before it reaches `crane`; state explicitly whether `ship-prepare` uses a **dedicated read-only GitHub App** (recommended) instead of the code-deployment app key, or record why not. Add WT-04b (hostile repo/tar; env dump + file read attempts in the clone/tar/crane path must find no secret) to the hostile matrix §7.4 and SR-01.

- [ ] **B-4 — OIDC scope of `ship-publish` has no hard prerequisite or fallback; it can overwrite the runner image** — §6 `ship-publish` row, V-8, DD-5, T16 (NFR-003, AC-007-4). The PRD places the runner image `exampleregistry.azurecr.io/githubrunner/devopsrunner` in the same registry. AcrPush on the registry is registry-wide; the spec limits it to `selfserve/*` only "if the registry is ABAC-enabled — V-8", with no stated outcome if it is not. If not, a compromise of `publish` (see B-3 tar parsing) yields write access to the image that runs on every trusted job with broad credentials — a privilege-escalation chain from user code to the platform runner. **Fix:** make repository-scoped write a hard Phase-1 gate with a decided fallback: (1) ABAC role-assignment condition restricting to `selfserve/*` (Container Registry Repository Writer / Contributor), else (2) a separate registry for shipped images (Flux/`ImageRepository` take `image_name`, so this is config), else (3) block the pilot. Add a negative test to WT-09/SR-01: the `ship-publish` token cannot push, delete or untag `githubrunner/*`, and cannot write outside `selfserve/*`. Also record whether the federated-credential subject can additionally pin `job_workflow_ref` (custom OIDC subject claim) so a different workflow in flux-config using environment `ship-publish` cannot mint the token.

- [ ] **B-5 — Legacy status-route authorization will lock out the legitimate owners of existing AKS deploys (regression on pages the spec claims are unchanged)** — §3.6.3 "Legacy route", §4.1 #10, BT-22 (AC-013-7, AC-001-7, AC-015-4). Verified in code: `POST /api/aks-deploy` sets `triggered_by = req.user.email` **raw** (`routes/api.js:1699`; `aksService` forwards it unchanged), whereas the spec's rule (a) compares `sanitizeActor(user.email)` (lower-cased, charset-mapped) with the run-name `by=`. With the additive `run-name` (`by=${{ inputs.triggered_by }}`), a user with a mixed-case or apostrophe email gets `by=Alex.Smith@…` ≠ `alex.smith@…` ⇒ 403 on the status poll made by `AKSDeployPage.vue` for their own deploy. The spec also says BYO deploys without a source repo are "visible only to platform members", which contradicts the same change (after it they *do* carry `by=`), and says nothing about deploys in flight (no `by=`) at rollout. **Fix:** specify the legacy rule completely: compare `sanitizeActor(by) == sanitizeActor(user.email)` (normalise both sides) and parse `by=` for the legacy `Deploy <app>-<env> [CID:…] by=<raw>` shape with a permissive tail, not the ship regex; define behaviour for runs without `by=` (e.g. fall back to the job-log `Triggered by`/PR-body line the legacy code already reads, or allow authenticated viewers for N minutes after rollout and state the accepted risk); keep `{success,status}` shape. Extend BT-22 (mixed-case/apostrophe emails, no-`by=`, pre-change runs, BYO runs after change) and add an E2E/regression check that `AKSDeployPage` polling still reaches a terminal state for the triggering user.

- [ ] **B-6 — Multi-run attempts (`config_only` retry) have no defined status composition and the run-name contract is inconsistent** — §3.4 run-name/regex/inputs, §3.5 "Run lookup" ("a newer matching run supersedes older ones (`attempt` = match count)"), DD-10, BT-09/BT-10/BT-18 (AC-008-7, AC-013-1, AC-013-3, AC-005-6, AC-013-4). A retry run (`mode=config_only`) skips `build`/`scan` and runs only `prepare` steps 1–5 and `publish` steps 6–9, so it carries no `sha`, `version`, `digest`, `scanId`, `tarSha256` and marks build/scan `skipped`. If "newest wins" is applied literally the result page loses the version/digest/sha and shows Security check as skipped for an image that was scanned. Also: the §3.4 `run-name` template has no `retry_by`/mode, the parsing regex has an optional `retry_by`, and the input table names it `retried_by`. **Fix:** define `ShipStatus` as a fold over all runs of the correlation ID (oldest→newest): `prepare/build/scan/publish` stages, `version/sha/digest/scanId/settings` from the latest run in which that stage ran (not skipped by mode); `config_pr`/`pr`/`failure` from the newest run; `attempt` = number of runs; specify the retry run's own annotation (it must echo `config_image_tag` and the original run id) and one run-name template/regex/input name (`retried_by` vs `retry_by`, `mode=…`). Add fixture-driven BT-10 cases for run 1 (full, `CONFIG_PR_FAILED`) + run 2 (`config_only`, success) and the failure case where run 2 also fails.

- [ ] **B-7 — Correlation-ID lookup cannot meet AC-013-3 without a client hint, and contradicts the call budget** — §3.5 "Run lookup" ("No hint → scan ≤10 pages"; "works … until GitHub retention expires the run"), §8 budget ("Run lookup ≤ 5"), §3.10.1 deep link (AC-013-3 `must`, AC-014-3, NFR-011). Ten pages × 100 runs bounds discovery to the ~1 000 newest `ship-from-repo` runs; a deep link opened by a colleague/another browser, or any ship older than that window, returns 404 although the run is still retained. The deep link carries only the cid (the `since` hint exists only in the originating browser's Recent list), and a no-hint scan costs up to 10 calls against a budget of 5. **Fix (one deterministic option):** mint the ship ID as a **UUIDv7** (server-side, time-ordered; accept version-7 nibble in the validator) so the backend derives the `created=` search window from the ID itself, making `since` unnecessary and the lookup ≤1–2 calls at any age within retention; alternatively embed a base-36 timestamp in the ID or put `&t=<epoch>` in the deep link and Recent entries (weaker: shared links without `t` still fail). Update BT-09 with "ship 30 days old, 2 000 newer runs" and keep the 404/`queued` grace semantics.

- [ ] **B-8 — Phase 1 verification gates are not testable gates, and a destructive behaviour depends on an unverified one** — §2.4 V-1…V-10, §11 Phase-1 gate ("V-gates recorded"), DD-7, DD-8, §9.3 WT-01/02/05, §5.2 (`.github/ship-fixtures/`) (testability dimension; NFR-005, NFR-008). Each gate lists "Verify" and "Fallback" but no pass/fail criterion, evidence artefact, decider, or which later phase it blocks; "recorded" is satisfied by a failing result. Several outcomes change contracts that QA and Dev will build against in parallel immediately after approval (V-3 → whether the whole annotation channel, BT-11 and `shipStatusService` exist or an artifact reader is needed; V-4 → `queuedBehind`, DD-7, DD-8, BT-19/BT-20; V-2/V-6/V-8). DD-7 **auto-cancels the run from a status GET** when a trusted job is "queued > 10 min and not concurrency-blocked", but V-4 (can the API distinguish runner-queued from concurrency-pending?) is unresolved; if they are indistinguishable the watchdog cancels legitimate ships queued behind a 30-minute `publish`. Finally the fixtures plan cannot run as written: ship builds the repo root of `org/repo` (monorepo sub-path is a PRD non-goal), so sample/hostile "repos" under `flux-config/.github/ship-fixtures/` cannot be shipped, and nothing says how flux-config CI dispatches a fixture with a valid `requester_github_login` while H-2 is open. **Fix:** replace §2.4 with a table of: measurable pass criterion, evidence file (e.g. `docs/SHIP-FROM-REPO-RUNBOOK.md#v-3`), decider (named role), blocks (which phase/BT/WT), outcome-on-fail with the exact spec sections that change; mark V-1, V-3, V-4, V-8, V-9 as hard gates for merging the status resolver / enabling the flag; add V-11: dispatch on the dedicated ref works and a dispatch on any other ref fails at the environment gate (DD-11/H-5), and extend V-1 to assert the `deploy-preview` run used the shipped tag. Make DD-7's cancel side-effect **off by default (report-only `RUNNER_UNAVAILABLE`)** until V-4 passes, and restrict it to `prepare` jobs (or to cases where no other run of the same app has an active `publish`). Specify fixture repos (separate repos in an allowlisted org with the Code App installed) and the CI dispatch path with a test login.

## Advisory Findings
- **A-1 — H-1…H-8 handling is internally inconsistent** — spec.md header ("None blocks Phase 1/2 implementation work") vs §2.3 (H-6 "Blocks: Phase 1"); §11 Phase-4 gate lists only H-1…H-4 although H-5 gates security sign-off, H-6 Phase 1 and H-8 the Phase-3 composable. Make §2.3/§11 agree; require H-8 and H-6 decisions before Phase 3/Phase 1 respectively; say H-3 "waiver" owner.
- **A-2 — Job permissions table is incomplete** — §3.4 jobs table: `prepare` has `contents: read` only but step 5 reads PRs, and `publish` step 9 resolves the PR by head branch; both need `pull-requests: read`. Confirm `actions: write` also covers `gh run list/view`. Cheap to fix in the revision; also add it to V-gates so it is exercised.
- **A-3 — DD-2 holds an `ubuntu-latest` slot while waiting on a job that needs another slot on the same pool** — verified: `generate-webapp-config.yaml` is `runs-on: ubuntu-latest`. Under pool saturation N waiting `publish` jobs can starve their own config runs until the 10-min timeout, producing correlated `CONFIG_PR_FAILED`. Add a saturation case to LT-01, document minimum pool size/runner-group headroom in the runbook, and consider a short poll-based wait with an early "config run not started in 3 min" signal.
- **A-4 — H-2 recommended Option A has no browser-facing contract** — no connect/callback/disconnect endpoints, header name, state/CSRF handling, or Connect CTA in S2 (S2 copy says "Ask the platform team to link it", which fits B/C, not A). Storing a user-to-server token in `sessionStorage` is XSS-reachable (spec's own T11); prefer a server-held, encrypted, httpOnly session. State explicitly that choosing A triggers a spec delta and a delta re-challenge rather than "mechanism-independent".
- **A-5 — H-5/DD-11 default is insecure-by-default but the open question is partly answerable now** — `SHIP_WORKFLOW_REF` defaults to `main`. Evidence at review time: none of the 16 flux-config workflow files on `main` uses `actions/cache` or a setup-action `cache:` input, so the practical poisoning surface is currently empty; record that, add a CODEOWNERS/lint rule forbidding `actions/cache` (and `setup-*` `cache:`) in flux-config, and fail closed (refuse to dispatch) when `workflowRef` equals the default branch unless an explicit `SHIP_ALLOW_DEFAULT_REF=true`. Note a workflow file normally must also exist on the default branch to be dispatchable; verify (V-11) that the dedicated-ref plan works.
- **A-6 — Authorization and abuse limits** — (a) rule (a) compares sanitised e-mail (lossy: `o'brien@x` and `o_brien@x` collide; e-mail is mutable); add a server-set `triggered_by_oid` input and compare the immutable Entra `oid`; (b) cancel and `retry-config-pr` are allowed to any reader of the repo (rule b) — restrict mutations to the starter or platform members; (c) DD-14's 12/h limit is global, so one user can exhaust everyone's budget and burn GitHub-hosted minutes (30-min builds): add per-user caps (e.g. ≤3 active, ≤6/h per `oid`) and a global max-active-ships limit.
- **A-7 — DD-7 cancel-on-read is scope beyond AC-011-7** — the PRD requires *reporting* `RUNNER_UNAVAILABLE`; the spec adds a state-changing side-effect on a GET, executed by whichever replica/viewer polls. If kept after B-8, log it, bound to one cancel per run (already idempotent) and require the actor to be the starter/platform member.
- **A-8 — Reserved namespaces** — `namespace` is user-chosen DNS-1123; the config workflow only rejects collisions with `namespace.yaml` files in the repo, so `kube-system`, `flux-system`, `default`, `cert-manager`, etc. pass and `preview-on-pr` deploys before any CODEOWNERS review. Add a denylist (`kube-*`, `flux-*`, `default`, platform namespaces) to `shipValidators` and BT-01.
- **A-9 — Budget and classifier gaps** — §8 budget omits: endpoint #4 (`/apps/:env/:app` does 2–3 GitHub reads + optional ACR per call with no stated cache/debounce key, while AC-002-7 implies per-edit calls), `GET /orgs/{org}/installation` (1 h cache, fine), per-poll PR read after publish, and ownership/permission re-checks on every authorised status call; add a cache key and a debounce rule and recount. `BUILD_TIMEOUT` relies on matching GitHub's system annotation text ("maximum execution time") — brittle; also derive from job duration ≥ `timeout-minutes` and include in a V-gate.
- **A-10 — Contract nits** — (1) input table has 15 inputs, spec says "14 of 25"; (2) JSON test catalog does not name FT-14 (S1 "no environment enabled") although md §9.2 does; (3) deep link `?ship=<cid>` can be lost across the MSAL login redirect (`redirectUri: window.location.origin`) — add an FT/E2E case for unauthenticated deep-link open; (4) AC-008-1 says `image_name` = `selfserve/<app>` but the dispatch passes the registry-qualified name (justified in §1.3) — note the PRD-wording deviation in the AC-008-1 traceability row; (5) ownership label is a repo URL: repo rename/transfer locks the owner out — add a runbook procedure; (6) the `SUPERSEDED` vs `CANCELLED` flag is per-process (acknowledged), keep BT-20 explicit about multi-replica behaviour.
