# PRD Challenger Review: kong-api-self-service (Round 1)
Date: 2026-07-22
PRD: docs/prd/kong-api-self-service.md

## Verdict
changes_requested

## Blocking Findings

- [ ] **Contradictory duplicate-handling semantics between FR-001(f) and NFR-REL-002** — FR-001(f) says a duplicate service name in the same environment must be rejected with `HTTP 409` before any workflow is dispatched. NFR-REL-002 says resubmitting "the same Kong service registration (same name + environment)" must be treated as idempotent and return `HTTP 200` with the existing service details — explicitly "not 409" in spirit. The PRD never defines what distinguishes a genuine naming conflict (409) from an idempotent retry (200): is it the same name with different payload vs. an exact-match resubmission? As written, two acceptance criteria specify different, mutually exclusive HTTP responses for what looks like the same trigger condition. **Fix**: Add an explicit rule, e.g. "if name+environment match an existing service AND the submitted payload (upstreamUrl, routes) is identical, return 200 with existing details (NFR-REL-002); if name+environment match but the payload differs, return 409 (FR-001f)" — and cross-reference this rule from both requirements.

- [ ] **Self-contradictory acceptance criterion in FR-002(d)** — "the workflow verifies no active traffic (P95 requests in last 5 min > 0) before proceeding" is logically inverted: verifying "no active traffic" should mean a request count of **0**, not `> 0`. As literally written, an implementer could build the exact opposite safety gate (block deletion only when traffic is absent). This gates a destructive, non-trivially-reversible action (route deletion), so the ambiguity carries real risk. **Fix**: rewrite as "...verifies no active traffic (P95 requests in last 5 min == 0) before proceeding; if traffic > 0, flag a warning and require an override flag."

- [ ] **Undefined metrics/data source for the FR-002(d) traffic check** — No FR, NFR, dependency, or API endpoint anywhere in the PRD names the system that will supply "P95 requests in last 5 min" for a Kong route (Konnect Vitals API? Analytics API? An external APM?). Section 4's evidence table and Section 8's API impact table are silent on any observability integration with Kong. Without a named source, Phase 3 cannot implement this safety gate. **Fix**: Add an explicit dependency/FR naming the metrics source (e.g., "Kong Konnect Vitals API, workspace-scoped, called from the GitHub Actions workflow"), or descope the check to a manual/warning-only confirmation for v1 and mark the automated check as a future enhancement.

- [ ] **Incorrect evidence citation for the "GitHub-as-database (metadata)" row (Classification accuracy)** — Section 4's Evidence Table attributes reading of `docs/metadata/*.json` to `services/infrastructureService.js` `_fetchDataFile()`. Verified against the actual code: `_fetchDataFile()` (lines 15–37) only reads **static config files under `data/`** (templates.json, modules.json, agents.json, roles.json, environments.json) via `data/${fileName}` on the `SERVICE_CATALOG_BRANCH`, with a local-file fallback. It never reads `docs/metadata/`. The methods that actually read `docs/metadata/*.json` are `getInstalledApps()` and a separate direct-lookup path (~lines 140–170, 637–663) that already solved an N+1 problem for per-app lookups ("FR-007: Primary lookup — docs/metadata/{projectName}-{environment}.json (direct, no N+1)"). This citation error could lead the Architect to wire the proposed `getKongServices()`/`getKongService()` (FR-008) onto the wrong existing method. **Fix**: Correct the Evidence Table row and point FR-008's proposed methods at the `getInstalledApps()`-style pattern instead of `_fetchDataFile()`.

- [ ] **Classification Matrix commits to the agent-dispatch pattern, but no FR or API endpoint actually uses it** — Section 5 classifies "Agent-dispatch pattern for incremental changes" as `existing-extend`, proposing to "Add a `kongConfig` agent entry to `data/agents.json`" and citing `POST /api/agent-change` (`routes/api.js` line 1354, confirmed to exist). However, Section 8's full API surface defines a parallel, independent REST namespace (`POST /api/kong/services`, `POST /api/kong/services/:name/:env/plugins`, `POST /api/kong/consumers`, etc.), and none of FR-001 through FR-010 mention `/api/agent-change` or `data/agents.json` at all. This is a direct contradiction between a stated architectural decision and the concrete requirements — the Architect has no clear signal on whether incremental Kong changes (FR-002, FR-003) should route through agent-dispatch or the new Kong-specific endpoints. **Fix**: Either remove the agent-dispatch row from the Classification Matrix, or reconcile it explicitly (e.g., state that FR-002/FR-003 route through `/api/agent-change` and update those FRs' acceptance criteria and Section 8 accordingly).

- [ ] **NFR-SCALE-001 target is unachievable under the described architecture without an undisclosed design addition** — Achieving ≤2s P90 load with up to 500 Kong service metadata files — each presumably a separate GitHub file fetched via the Contents API, consistent with the existing `docs/metadata/` pattern — is very unlikely on a cold cache. Listing + fetching hundreds of individual files (or even a batched git-tree fetch) typically costs multiple seconds of GitHub API round-trip time alone, before any pagination logic runs. The PRD's stated strategy ("Paginate the inventory API (page size = 50 default); lazy-load additional pages on scroll") only helps once data is already in memory — it does not address the cost of populating that data given there is no real database. **Fix**: Either lower/qualify the NFR target for cold-cache scenarios (e.g., "≤2s only when server-side cache is warm; cold-cache target is Xs"), or add an explicit FR/design dependency for a caching/indexing layer (e.g., a periodically refreshed server-side index) before this NFR can be verified as currently stated.

- [ ] **FR-004(d) introduces an unlisted hard dependency on Key Vault provisioning** — "Credentials are stored in an Azure Key Vault provisioned for the consumer team's application (requires either an existing Key Vault in the team's infra metadata or creation of one as a prerequisite step)" implies an entire additional provisioning workflow that is not declared in FR-004's Dependencies field (which lists only FR-001, FR-005, NFR-SEC-002), not scoped as its own FR, and not mentioned in Section 10's Risks/Assumptions. A consumer team with no existing Key Vault has no defined implementation path to complete FR-004 as written. **Fix**: Add an explicit FR or Assumption (with owner) covering "Key Vault existence check and on-demand provisioning for consumer teams," or descope FR-004 in v1 to only support teams that already have a Key Vault in their infra metadata.

## Advisory Findings

- NFR-USE-001's usability test uses a sample of 2 developers to validate a ≤10-minute task-completion target that also gates the Definition of Done — consider a larger sample or explicitly labeling this as directional rather than a hard gate.
- FR-004's Dependencies field doesn't reference Assumption A6 (Dev Portal licensing), even though Section 10 and the Delivery Plan (Phase 3) treat A6 as the deciding factor for whether FR-004 ships at all — add the cross-reference for clarity.
- The proposed `data/modules.json` extension for a `kongService` entry (Section 8) is speculative ("potential future integration with the Custom Infrastructure wizard") and is not required by any FR — the primary UX flow uses a dedicated Kong page, not the module wizard. Recommend removing it from v1 scope or explicitly labeling it as future/optional.
- Minor wording inconsistency in FR-004: (b) allows selecting "one or more published Kong Services" (plural) but (e) states "the target service to be active" (singular) — clarify whether a multi-service subscription requires all selected services to be active, or each independently.
- The Delivery Plan's Phase 2 gate depends on "GitHub Actions workflow for Kong service creation available in infra-live," but building that workflow is never listed as an explicit Phase 1 deliverable — recommend adding it once OQ-4 (delivery mechanism) resolves.
- The `PUT /api/kong/services/:serviceName/:environment/routes` endpoint handles both adding and removing routes through one verb/path — unconventional REST semantics that may complicate clean audit-log `action` values required by FR-010(a)/(b). Consider splitting into distinct add/remove operations.
