## Blocking Findings

- [ ] **Pre-existing unconditional `oneOf()` shape validator rejects every bundle-mode request before it reaches any bundle logic** — `routes/api.js` lines 313–333. The `POST /api/secrets` handler's existing `check(...)` chain includes an **unconditional** `oneOf([[secrets[] shape], [secretName/secretValue shape]], { message: 'Request must include either a secrets[] array (1-20 entries) or a legacy secretName/secretValue pair' })` (lines 323–333), evaluated by express-validator as part of the same top-level chain regardless of which top-level fields are present. A bundle-mode request per spec.md §3.3 carries `bundleId` + `environmentSecrets[]` and supplies **neither** `secrets[]` **nor** `secretName`/`secretValue`, so both `oneOf()` branches fail, `validationResult(req)` is non-empty, and the handler returns `400` at line 366 — **before line 369's manual XOR check, and before any bundle-membership/resolution logic ever executes.** Spec.md §3.3 ("Validator additions") lists new `check('bundleId')`/`check('environmentSecrets')...` chains and correctly proposes extending the *manual* 2-way `hasSingular === hasArray` JS check (lines 369–382) into a 3-way XOR — but it never mentions modifying, gating, or bypassing this separate, earlier, unconditional `oneOf()` block. Verified directly by reading `routes/api.js` lines 313–333 and 338–366: the two checks are structurally independent (one is an express-validator chain evaluated at `validationResult()`, the other is post-validation manual JS), and fixing the second does nothing to the first. This blocks FR-005/FR-006 (the PRD's core `must` requirements) from ever being reachable exactly as specified — every bundle-mode submission would 400 with a misleading "secrets[] or secretName/secretValue" error. **Suggested fix**: make the existing `oneOf()` conditional on the absence of `bundleId` (e.g., wrap it in a custom check with `.if((value, { req }) => !req.body.bundleId)`, or restructure into a true 3-way `oneOf()`/dispatch that validates whichever discriminator field — `secrets`, `secretName`+`secretValue`, or `bundleId`+`environmentSecrets` — is actually present), and have spec.md's §3.3 explicitly call out this change to the *existing* `oneOf()` block, not only the manual XOR extension.

- [ ] **`createMultiFileCommit()` has no write-time compare-and-swap; the documented "pre-write SHA conflict → 503" error scenario cannot fire for its own final write window** — spec.md §2.4 (method signature, lines 248–272), §2.5 (submission algorithm), spec.json line 146/276 (`"pre-write SHA conflict"` / `"a target file's SHA drifted between pre-flight capture and write (concurrent edit)"` → 503). The existing single-file precedent (`secretsService.submitSecretViaGitOps()`, lines 714–849) gets genuine optimistic-concurrency protection for free because its final write (`githubService.createOrUpdateFile()` → `octokit.rest.repos.createOrUpdateFileContents({ sha })`) is validated **by GitHub itself** at write time: if the supplied `sha` doesn't match the file's current blob SHA, GitHub rejects the write atomically. `createMultiFileCommit()` (verified via spec.md lines 248–272: `getRef` → `getCommit` → `createTree` → `createCommit` → `updateRef({force:false})`/`createRef`) has **no equivalent per-path SHA check** — `createTree` unconditionally writes the given `files[]` content regardless of what the fetched `base_tree` actually contains for those paths at that instant, and `updateRef({force:false})` only guards non-fast-forward ref moves (same-branch races), not a conflicting write to the same `secrets.enc.yaml` blob landing between the pre-flight check and this call. The submission algorithm's own SHA check (§2.5, "getFileContent per included env (pre-SHA capture)" → encrypt → re-check) only brackets the **encryption-latency window**; there remains an unprotected window between that re-check and `createMultiFileCommit()`'s own internal `getRef`/`getCommit` fetch, during which a conflicting write would be **silently overwritten with no CONFLICT/503 raised** — directly contradicting the documented error scenario's own name ("pre-write SHA conflict") and undermining FR-005(d)'s explicit claim to "mirror the existing... precedent" and NFR-REL-001's no-silent-data-loss intent for a security-sensitive artifact. The architecture deep-dive doc itself is honest about this gap ("Trade-off: this method does not itself handle SHA-conflict detection... callers remain responsible for pre-write conflict checks," `20260918-git-data-api-atomic-commit.md` lines ~81-84) — but the calling spec (spec.md §2.5) does not actually close that gap for the true final-write window, it only re-checks earlier. **Suggested fix**: have `createMultiFileCommit()` accept an `expectedFileShas: Record<path, string|null>` map and, after fetching the base tree (data already in hand from the existing `getRef`/`getCommit`/tree walk — no extra API call needed), verify each target path's current blob SHA against the expected value before calling `createCommit`/`createRef`/`updateRef`, throwing `CONFLICT` on any mismatch. This closes the gap to match the guarantee the single-file precedent gets for free from GitHub's Contents API, and makes the documented "pre-write SHA conflict" error scenario actually true to its name.

- [ ] **NFR-OBS-001's "100% of log lines carry correlationId+bundleId" target has no design path to be met for the commit/PR-creation phase** — PRD NFR-OBS-001 (a `must`-priority NFR, `docs/prd/secrets-environment-bundles.md` lines 750–758) requires "100% of log lines emitted during a bundle submission (**pre-flight resolution through commit/PR creation**)" to carry `correlationId` and `bundleId`. Verified against the actual code and the spec's own method signature: `createMultiFileCommit(repo, { branchName, baseBranch, files, commitMessage })` (spec.md §2.4, line 248) takes **no `correlationId` parameter**. This mirrors — and does not override — `githubService.js`'s existing convention: `createBranch()` (`logger.info('Branch created: ${newBranch} in ${repo}')`, line 259), `createPullRequest()` (`logger.info('Pull request created: ${response.data.html_url}')`, line 225; `logger.error('Failed to create pull request: ...')`, line 231), and `getRepoTree()`'s `logMetric` call all log **without** `correlationId` today, and neither spec.md nor spec.json proposes threading it through for the new or reused calls this feature depends on (`createMultiFileCommit`, `createPullRequest`). Separately, `secretsService.submitSecretViaGitOps()` (lines 714–849) — the function this feature's own §2.5 claims to "mirror" — itself emits **zero** intermediate `logger.*` calls; the only correlationId-tagged, structured emission anywhere in the existing single-secret flow is the route-level `logMetric('secret_create_submitted', ...)` call. Spec.md §7 only commits to extending that same single final `logMetric` call with new fields (`bundleId`, `releaseControlled`, `includedEnvironments`, `excludedEnvironments`, latencies) — it never specifies *any* log line design for the resolution/encryption/commit/PR-creation phases beyond that one final call and the unrelated bundle-config-loader error logs (`loadSecretBundles`, lines 187/192, which do carry correlationId but predate/are unrelated to a specific bundle submission). Since NFR-OBS-001's literal, `must`-priority target explicitly includes "through commit/PR creation," and the concrete methods invoked in that phase are specified/reused without correlationId, this NFR's stated 100% target is not actually achievable as designed — a "log-line assertion test" (which spec.md §4.2 commits QA to writing) would fail against the current design. This is a pattern-violation-caliber gap (missing correlationId threading is explicitly called out as a Blocking example in this review's own charter). **Suggested fix**: either (a) thread `correlationId` (and ideally `bundleId`) as an explicit parameter into `createMultiFileCommit()` and the bundle-mode call to `createPullRequest()`, having them include it in their own log lines, or (b) more minimally, have `secretsService.submitSecretBundleViaGitOps()` (the new service-layer function) emit its own explicit `logger.info(`[${correlationId}] [${bundleId}] ...`)` lines wrapping each phase (resolution complete, encryption complete, commit created, PR created) so 100% of *service-layer* log lines satisfy the NFR, and have spec.md explicitly scope NFR-OBS-001's "every log line" language to the service-layer's own emissions (excluding githubService.js's pre-existing, out-of-scope internal logs) so the target is both true and testable as written.

## Advisory Findings

- **Diagnostic-only misconfigured-bundle-member log line slightly overstates being "free"** — spec.md §7 states this "piggyback[s] on the existing tree-scan pass already performed by `resolveKeyVaults()`/`discoverAppsForTarget()`." The raw data (all discovered `{name, environment, qualifier}` triples) does already flow out of `discoverAppsForTarget()`'s existing tree scan, so no *new* GitHub API calls are needed — but detecting "a configured bundle environment that never matches any discovered environment across a full tree scan" requires a **global set-difference** (union of all discovered environment names across all apps, diffed against each bundle's declared `environments[]`), which is a different computation than either function currently performs or exposes (they classify one given environment against one bundle, not enumerate global membership gaps). Not a new API cost, but a small new reducer function the spec doesn't call out as new work. Recommend spec.md clarify this is "no new API calls, but a new small aggregation step," so implementation estimates aren't understated.
- **`spec.json`'s unit-test enumeration for `resolveBundleEnvironments` doesn't explicitly name all documented reason codes** — spec.json's data-contract validation lists `NOT_DEPLOYED`, `QUALIFIER_AMBIGUOUS`, `QUALIFIER_MISMATCH`, `VAULT_AMBIGUOUS`, `VAULT_INVALID` as valid exclusion reasons (spec.json line ~311), but the `unit_tests` array for `resolveBundleEnvironments` (spec.json lines ~524–532) only names test cases for the ambiguous-vault/qualifier and successful-disambiguation paths — `QUALIFIER_MISMATCH` and `VAULT_INVALID` are not named as distinct test rows. QA can still infer coverage is needed from the reason-code taxonomy, but an explicitly named test row would remove any guesswork, consistent with this project's own recorded lesson (spec.md line ~580 cites a prior redaction gap that "only an executable test caught"). Recommend adding explicit test rows for the two missing reason codes.
- **No existing precedent for an accessible editable data-entry grid in this codebase** — searched `srcV2/` for `role="grid"`, `aria-rowindex`, `role="gridcell"`: zero matches. Existing `<table>` usage (`InstalledAppsPage.vue`, `AKSInstalledAppsPage.vue`, `RbacManager.vue`) is read-only display, not an editable per-cell input grid. `BundleSecretGrid.vue` (spec.md §2.7/§4) is genuinely novel UI territory for NFR-USA-001's keyboard-operability target, and inventing a full ARIA `role="grid"` + roving-tabindex pattern from scratch is a well-known accessibility footgun if done incorrectly (harder to get right than the simpler alternative). Recommend the spec explicitly steer Vue.js Dev toward a semantic `<table>` with native `<input>` cells (which gets correct Tab/Shift+Tab operability for free from the browser, no custom ARIA roving-tabindex needed) rather than leaving the pattern choice fully open, to de-risk the axe-core 0-violations target.
- **Carry-forward of PRD Round 2's Security/Compliance sign-off advisory is not tracked as an action item in the spec** — the approved PRD Round 2 review (`docs/reviews/secrets-environment-bundles-prd-review-round2.md`, lines 27–31) flagged that Security/Compliance (a named PRD stakeholder) has not recorded explicit sign-off on FR-007(e)'s `stage`/`cint`/`hot`/`demo` dual-classification resolution. Spec.md §9.1 correctly notes this is "handled entirely by FR-007(e), unchanged by this spec" but does not re-surface it as an open action item for whoever owns Phase 3 rollout sign-off (it does this well for OQ-001 in §1.2/§9.2, but not for this carried-forward item). Recommend the spec's risk register explicitly list this alongside the OQ-001 Definition-of-Done recommendation so it isn't dropped before Phase 3.
- **Per-entry redundant bundle-config parsing is a latent performance smell, not covered by a named NFR** — `discoverAppsForTarget()`'s per-app-entry map (mirroring the existing `classifyEnvironmentTier()` per-call synchronous `fs.readFileSync` pattern, `services/secretsService.js` lines 552–565) would, if `classifyBundleMembership()`/bundle lookups follow the same per-entry pattern, re-parse/re-validate the whole bundle config file once per discovered app/environment entry within a single `GET /api/secrets/apps` request. Not required by any PRD NFR target for that endpoint's latency, so not blocking, but worth flagging for SRE DevOps/Vue.js Dev to consider caching the parsed config once per request rather than per entry.

## Round Context
This is Round 1 — the first full Architecture Challenger review of this spec package. There is no
prior round to compare against. All nine review dimensions (PRD traceability, JSON/MD consistency,
pattern compliance, contract clarity, testability, NFR realism, error-scenario completeness,
security/compliance blind spots, escalation-trigger consistency) were checked against the spec and
cross-verified against the live codebase (`routes/api.js`, `services/secretsService.js`,
`services/githubService.js`, `CODEOWNERS`, `data/environmentTiers.json`, `srcV2/pages/SecretsPage.vue`,
`srcV2/services/api.ts`, and existing test files).

Positive findings worth recording (not gaps): all 9 FRs and all 8 NFRs from the PRD are explicitly
traced in spec.md/spec.json; `spec.json` and `spec.md` are otherwise mutually consistent (no drift
found in endpoints, data contracts, or NFR targets — including consistently missing the same
validator-collision defect in both, which is a substantive design gap present identically in both
artifacts rather than a JSON/MD sync issue); the "no new GitHub App scope" claim for Git Data API
usage is technically sound (GitHub scopes the entire Git Data API family under the same "Contents"
permission already used by `createBranch()`); the OQ-001 stakeholder-assertion treatment (§1.2/§9.2) is
appropriately conservative — independently re-verified via GitHub MCP `get_file_contents` against both
`infrastructure-live` and `service-catalog` (both `404 Not Found` from this workspace), matching the
Architect's own re-verification result, so this is correctly treated as an evidence gap rather than
resolved; the ADR (`20260918-atomic-bundle-commit-supersedes-fanout.md`) and architecture deep-dive doc
(`20260918-git-data-api-atomic-commit.md`) were both appropriately triggered per the Architect's own
escalation rules and are internally honest about trade-offs (the deep-dive doc's own "does not itself
handle SHA-conflict detection" caveat is what led to Blocking Finding #2, so its existence is a credit
to the Architect, not a gap); the documented branch-reuse idempotency edge case (§2.6) is an honest,
adequately-handled carry-forward of existing behavior, not a new flaw.
