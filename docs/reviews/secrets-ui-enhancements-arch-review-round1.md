## Blocking Findings

- [ ] **FR-001(e) environment-derivation algorithm for `target=live` is unspecified, and the chosen data source structurally can't produce it as described** — reference: FR-001(a)/(d)/(e) (`docs/prd/secrets-ui-enhancements.md`), OQ-001 Design Decision in spec.md. The PRD's `must` AC FR-001(e) requires environments to be derived from the `infrastructure-live` directory structure, and FR-001(d) requires the response to include `{name, environment}` pairs. The Architect's OQ-001 resolution picks the `resolveKeyVaults` tree cache over `hclParser.getApplicationsFromRepo()` "to avoid a second GitHub call," but only describes extracting **app names** ("first path segment after `infrastructure/`") — it never states how the **environment** half of the pair is derived from tree entries. Verified against the actual code (`services/secretsService.js` `matchVaultsFromEntries`): that function takes a known `appName`+`environment` as *input* and filters the tree down to vaults for that specific pair — it has no "enumerate every environment for every app" mode. Building that reverse enumeration is new logic, not a reuse of an existing function, and it isn't specified. It also isn't clear the tree-based approach can even see an environment that doesn't yet have a `keyvaultN` directory/file (unlike `hclParser`, which enumerates `env.hcl` files directly per environment) — meaning `target=live` could silently omit valid environments that have no Key Vault yet, which is a functional regression the PRD's Goal 1 explicitly tries to prevent (mismatched/incomplete app-env lists).
  **Fix**: Add a concrete algorithm to spec.md, e.g.: "for each tree entry matching `infrastructure/{app}/{env}/...`, treat every second path segment as a candidate environment regardless of whether a `keyvaultN` marker exists under it; dedupe `{app, env}` pairs across the whole tree." State explicitly whether an app with zero vaults anywhere still appears (with an empty vault list) or is excluded, and reconcile that against FR-001(e)'s directory-structure-based requirement.

- [ ] **Legacy singular-shape vs. new `secrets[]`-array-shape validation via `express-validator` is not specified, and the two shapes are mutually exclusive under static `check()` chains** — reference: FR-003(a)/(b), spec.md "Modify: `POST /api/secrets`" bullet, spec.json `technical.components.backend[0].endpoints[1].validation`. Verified against the current code (`routes/api.js` lines ~260-268): today's validators are `check('secretName').matches(...)` and `check('secretValue').isString().notEmpty()` applied unconditionally to every request. If the new `secrets[]` array becomes the primary shape, a request using the legacy singular fields (no `secrets[]` key) will fail whatever new `check('secrets').isArray(...)` chain is added, and vice versa — `express-validator`'s declarative chains don't branch on "which shape is present" without an explicit `oneOf([...])`/`.custom()` construct. The spec never states which mechanism resolves this, so an implementer could easily ship a version that silently breaks one of the two shapes (most likely the "backward compatible" legacy path, since that's the one nobody will manually test against the new form).
  **Fix**: Specify the exact validation strategy, e.g. `oneOf([[check('secrets').isArray({min:1,max:20}), ...], [check('secretName').matches(...), check('secretValue').notEmpty()]])`, or a single `.custom()` validator that normalizes the body into `secrets[]` before the rest of validation runs. Add an explicit integration test asserting both shapes independently pass validation.

- [ ] **FR-001(g)'s "5-minute cache" for `target=sand` claims to reuse a cache module that doesn't exist** — reference: FR-001(g) (PRD), spec.md Component Changes bullet "Result cached 5 min per target (reuses existing cache module)." Verified against `services/infrastructureService.js`: `getInstalledApps()` (lines ~143+) has **no caching at all** — every call is a fresh GitHub read. Only the `target=live` path benefits from an existing cache (`secretsService`'s `treeCache`/`getCachedTree`, used by `resolveKeyVaults`). The spec's claim of "reuses existing cache module" is therefore only true for one of the two targets; for `sand`, a net-new cache (key, TTL, eviction-on-error semantics) must be designed from scratch, and none of that is specified. Left as-is, an implementer following the spec literally could conclude no new caching work is needed for `sand`, silently failing FR-001(g) and risking NFR-PERF-001 (3000ms p95) under repeated target toggling.
  **Fix**: State explicitly that `discoverAppsForTarget` needs its own new per-target cache (mirroring `treeCache`'s Map-of-promise-with-TTL-and-evict-on-rejection pattern for consistency), covering both `live` and `sand` results, not just re-use of the tree cache for `live`.

- [ ] **Bulk branch-name hash algorithm is underspecified, blocking a deterministic unit test** — reference: FR-003(e)/OQ-002 (PRD, resolved), spec.md Design Decisions table, spec.json unit test "Bulk branch naming with shortHash." The PRD/spec state the branch suffix is "the first 8 characters of a SHA-256 of the sorted secret names," but never specify the exact string fed into SHA-256 (e.g., `sortedNames.join(',')` vs `sortedNames.join('')` vs `JSON.stringify(sortedNames)`, case-folding, delimiter). Without this, the QA/Dev agents writing and asserting the exact expected branch name in "Bulk branch naming with shortHash" (spec.json `testing.unit_tests`) will each have to invent a serialization, and a mismatch between the implementation's choice and the test's expectation will produce a false failure that has nothing to do with a real defect.
  **Fix**: Pin the exact algorithm in spec.md, e.g.: `crypto.createHash('sha256').update(sortedNames.join(',')).digest('hex').slice(0, 8)`, and mirror it verbatim in the JSON unit test description.

- [ ] **NFR-SEC-001's "zero `secretValue` in error responses" claim is not backed by any sanitization of `express-validator`'s default error output** — reference: NFR-SEC-001 (extended), spec.json `nfrs.security[0]` ("No secretValue in logs, PR descriptions, metric payloads, or error responses"). Verified against `routes/api.js`'s existing 400 handler: `return res.status(400).json({ success: false, errors: errors.array(), correlationId: req.correlationId })`. `express-validator`'s default `errors.array()` formatter includes a `value` field per failed check — the actual value that was submitted for that field — unless explicitly stripped. The spec doesn't call out any sanitization step before this reused 400 path ships for the new `secrets[]`/`secretValue`-bearing validators. Today's practical exposure is low (the only `secretValue` check is `notEmpty()`, which only fails on an empty string), but the spec is adding new validators around a bulk array of secret values and explicitly promises "zero occurrences ... in ... error responses" as a measurable NFR target — an unconditional claim the current code path cannot actually guarantee once any stricter `secretValue` validator is added (e.g., a future max-length check).
  **Fix**: Specify that the 400 handler must map `errors.array()` through a redaction step (e.g., strip `value` for any `param` matching `secretValue`/`secrets.*.secretValue`) before responding, and add this as an explicit QA test case ("submit a secretValue that fails a validator and grep the JSON response for the value") rather than only "grep server logs" (current manual test list only covers logs, not response bodies).

## Advisory Findings

- Bulk-flow step ordering (existing `409 PR_EXISTS` dedup check, pre/post-write SHA conflict check, branch-create) relative to the N sequential SOPS encrypt calls isn't fully diagrammed in spec.md's mermaid sequence — only "encrypt all in memory" then "commit + PR" are shown. Recommend an explicit numbered flow (matching the level of detail in the existing single-secret `submitSecretViaGitOps`) so Vue.js Dev doesn't have to reverse-engineer ordering from the v1 code.
- NFR-PERF-002's 5000ms/20-secret budget is already correctly labeled provisional (inherited from the PRD), but the SHA-conflict race window (capture-before-encrypt, recheck-after) widens proportionally with batch size — up to several seconds for 20 sequential `sops` calls — increasing the false-positive 503 rate under concurrent edits to the same vault file. Worth a one-line note in spec.md's Testing/NFR section so QA doesn't mistake an occasional bulk-503-under-load as a functional bug.
- No PR title format is specified for the bulk case (only branch name and PR body content are). Recommend adding one for consistency with the existing single-secret `prTitle` convention (e.g., `Secrets update: {secretCount} secrets ({appName}/{environment})`).
- Minor internal JSON inconsistency: `technical.api_endpoints[1].validation` (top-level array) omits the legacy-singular-shape backward-compat note that IS present in the more detailed `technical.components.backend[0].endpoints[1].request_schema.secrets` description. Align the two so a reader of only the top-level `api_endpoints` array doesn't miss the backward-compat requirement.
- `error_scenarios` in spec.json lists only 3 cases (mid-batch encryption failure, concurrent submission, tree fetch failure). `SOPS_NOT_CONFIGURED` (503) is inherited unchanged from v1 but isn't explicitly enumerated for the bulk path — low risk since the generic `statusByCode` map in `routes/api.js` already covers it, but worth listing for QA completeness.
- FR-001(d)'s exact response shape is ambiguous on whether an app with multiple environments appears as multiple `{name, environment}` rows (flat list) or is grouped. Given the existing `appNames`/`filteredEnvironments` computed properties in `SecretsPage.vue` that this must feed, a one-line clarification (flat list, one row per app+env pair) would remove ambiguity for the frontend implementer.
