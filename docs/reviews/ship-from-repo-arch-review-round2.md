## Blocking Findings
- [ ] **N-1 — A `CONFIG_PR_FAILED` ship has no image-bearing run `I`, so the `config_only` retry (and the carried version/digest/scan stages) is unreachable; trusted-job annotation cardinality is also inconsistent** — §3.5 "Attempt composition" (`I` = "newest `mode=full` run whose `publish` annotation is valid with `ok:true` (publish job `success`)"), §3.5 "Trusted results" rules 1, 2 and 6, §3.4 `publish` steps 4/9, DD-3 ("exactly one `ship.result` annotation" per trusted job, from a "dedicated final step"), DD-10, §4.1 #9, BT-10 case 1, BT-11, §7.4 case 10 (AC-008-7 `must`, AC-013-1, AC-008-3/-5, B-2/B-6 closure). `publish` runs steps 1–5 (image) then 6–9 (config) in **one job**, and a failed or timed-out step 9 ⇒ `CONFIG_PR_FAILED` ⇒ the job concludes `failure` (nothing in §3.4 makes the config steps non-fatal; stage derivation for `config_pr` even keys on "step failed"). Rule 6 then discards the `publish` annotation's `ok:true` because the **job** did not conclude `success`, and the `I` definition requires "publish job `success`". Result: for exactly the scenario BT-10 case 1 and DD-10 are built around (run 1 full + `CONFIG_PR_FAILED`), there is **no `I`**: version/sha/digest/scanId are lost (fold falls back to `F` but `publish` is then `UNKNOWN`/failed), `retry-config-pr` is refused with `409 RETRY_NOT_APPLICABLE` ("`I` is missing"), and the `config_only` consistency check (`imageTag == I.version`, `originRunId == I.id`) can never pass. In addition `publish` must emit **two** `ship.result` annotations (stages `publish` at step 4 and `config` at step 9; rule 1 says "exactly one per (job, stage)"; rule 2 compares to "the expected stage for that job", singular), which contradicts DD-3, ADR 2, the deep-dive §3 and §7.4 case 10 ("exactly one annotation") and the `emit-result.sh` "final step" wording. QA and Dev would implement BT-10/BT-11 against contradictory rules. **Fix (spec-only, no new design):** (a) define validity per **step group**, not per job conclusion, for `publish`: the `publish` result is honoured iff the `Publish:` steps all succeeded (step conclusions from the same `jobs?filter=latest` call) **or** make `Config PR:` steps non-fatal to the job (`continue-on-error` + final `emit-result.sh` that sets the job exit status from the config result) — pick one and state it in §3.4, §3.5 rule 6 and the `I` definition; (b) state precisely: "`prepare`, `scan`: exactly one annotation each; `publish` job: exactly one annotation per stage tag (`publish` and `config`), exactly two in total in `mode=full` and exactly one (`config`) in `mode=config_only`", and align DD-3, ADR 2 §4, deep-dive §3 and §7.4 case 10; (c) add the BT-10/BT-11 fixtures: publish step 9 failed with valid `publish`+`config` annotations ⇒ `I` exists, `config_pr` failed, `retry:'retry_config'`; two `config` annotations ⇒ discarded; a `publish` job failed in step 4 with a forged `ok:true` ⇒ rejected. A Challenger delta check of these three edits is sufficient.

## Advisory Findings
- **N-A1 — Run-lookup bound is stated more strongly than the design supports** — §3.5 "Run lookup" says the window "contains only the ship's own first run and its possible retries"; it actually contains **every** `ship-from-repo` run dispatched in `[t−1 min, t+25 h]`. The ≤3-page claim holds only through DD-14's cap (12/h ⇒ ≈300 runs/25 h); caps are per replica (ASM-12) and fixture-CI/direct dispatches (WT-14) are not capped. Reword to "bounded by DD-14", add a per-page-count metric/alert, and clarify the ambiguous early-stop clause ("stops paging once `t+30 min` is passed and ≥1 run found and no more candidates can be a retry" — a retry can be created for up to 24 h). Also add the 24 h retry limit (ASM-10) as a **PRD deviation note** on the AC-008-7 traceability row (currently only AC-008-1 and AC-013-3 carry deviation notes).
- **N-A2 — Header status line disagrees with §2.3/§11** — spec.md header says "H-6, H-9 gate Phase 1 exit … H-10 gate the pilot"; §2.3/§11 say H-6 gates Phase 1 **start**, H-9 **and H-10** gate Phase 1 exit (V-8 is P1). Align the header (same class as Round-1 A-1).
- **N-A3 — DD-11 has no ADR and the deep-dive does not contain a DD-11 section** — the deep-dive says DD-11/DD-16 are "recorded in spec §2.1 and §4 below"; §4 covers DD-16 only. Accepted because DD-11 is a config/gating decision with a fail-closed default, but add a short DD-11 paragraph (dedicated ref, environment branch rule, cache-lint, fail-closed default) to the deep-dive so the cache-poisoning rationale lives next to the trust-zone rules.
- **N-A4 — UUIDv7 detail** — specify that `utils/shipId.js` uses the existing `uuid` v11 `v7()` (or the RFC 9562 layout from `crypto.randomBytes`) and that the millisecond clock is monotonic enough that two ships minted in the same ms still differ (random tail suffices); BT-26 already covers layout/windows, add "clock skew ≤ 2 min between replicas and GitHub" as an explicit ASM so the future-timestamp 404 cannot reject a legitimate fresh ship.
- **N-A5 — Fixture-CI dispatch identity** — `ship-fixtures-ci.yaml` uses a fixed `triggered_by_oid` (`00000000-0000-4000-8000-000000000001`) and `requester_github_login=ship-ci-bot`; document that this oid can never match a real Entra user (it is not UUID-v7/a tenant GUID) and that `ship-ci-bot` needs read-only access to the fixture repos only, so a fixture run can never be mistaken for a human starter in rule (a).
- **Round-1 advisories A-1…A-10 spot-check:** A-1 mostly done (see N-A2); A-2 done (`pull-requests: read`, V-1(c)); A-3 done (DD-2 saturation, 3-min `configQueued`, R-A2, LT-01); A-4 done (sealed httpOnly cookie, explicit spec-delta + delta re-challenge for Option A, S2 copy per provider); A-5 done (fail-closed default ref, cache lint, observation recorded, V-11); A-6 done (oid key, mutations starter/platform-only, per-user + global caps); A-7 done (report-only, prepare-only, once, logged); A-8 done (reserved namespaces in validators/workflow/BT-01, ASM-11 gate); A-9 done (budget recounted, endpoint #4 debounce/cache key, duration-based `BUILD_TIMEOUT`, V-10); A-10 done for items 1, 2, 3 (FT-16), 4, 5 (aliases), 6 (BT-20).

## New material reviewed — no defect found (beyond N-1/N-A*)
- **Ship Reader App / `ship-prepare` OIDC identity (DD-15, DD-5):** read-only, minting step only sees the key, registry read used before any repo bytes are touched under an isolated `AZURE_CONFIG_DIR`; runner-injected OIDC request variables are dropped by the `env -i` wrapper for clone/tar. Sound.
- **UUIDv7 ship IDs:** version/variant validator, future/expired 404 without GitHub call, negative cache + per-user miss cap, authorization never relies on ID secrecy (oid check on resolved runs). Sound; see N-A1/N-A4.
- **Annotation encoding (base64url, ≤4 KB raw, regex `^ship\.result\.v1:…:[A-Za-z0-9_-]{1,6000}$`):** 4096 bytes ⇒ 5 462 chars, within 6 000; no workflow-command escaping needed. Sound.
- **Status fold (apart from N-1):** per-part source table, `durationSec` sum, `UNKNOWN` on mismatched `originRunId`/`imageTag`, retry-in-`prepare` carries stages. Sound.
- **V-gate table / hard-gate classes (G-RES, G-FLAG, P1):** criteria measurable, deciders named, outcomes mapped to sections; "FAIL without an approved delta blocks". Sound.
- **Human decisions H-1…H-10, ASM-10/11:** every item is an explicit, scoped blocker or assumption with fail-closed defaults and a named phase gate (H-6 Phase-1 start; H-9/H-10 Phase-1 exit and flag; H-8 before the Phase-3 composable merge; H-1…H-5, H-7 and ASM-10/11 Phase-4/flag; H-2 Option A ⇒ spec delta + delta re-challenge). Appropriately modelled as human gates, not silent assumptions. Open decisions are **not** counted as Blocking findings.
